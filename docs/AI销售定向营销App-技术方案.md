# AI 销售定向营销 App · 技术方案

> 日期：2026-10-11 ｜ 状态：已定稿（2026-10-11 chen 确认选方案 B）
> 需求输入：PRD v1.0 —— 4 个 Tab（画像录入/分层洞察/话术生成/触达记录）＋全局设置，3 个 AI 调用点（一句话整理画像卡 / 五层分群＋策略 / 按画像生成三版话术），只生成不真发，人工确认链：生成 → 预览可改 → 复制 → 手动登记。
> AI 平台：千问百炼 OpenAI 兼容模式（https://dashscope.aliyuncs.com/compatible-mode/v1，model 用 qwen-plus，Key 存后端环境变量）。

本文给两个方案：A 纯前端单文件（备选）、B 前后端分离（主选，demo 用）。结论先行：**demo 用 B**（chen 有 2 核 4G 服务器，运维成本低）；A 作为备选保留。

---

## 方案 A：纯前端单文件（备选）

### 1. 技术选型说明

- 语言：HTML ＋ CSS ＋ JavaScript（原生三件套，不用 Vue/React 等框架）。
- 为什么：① 单文件，双击就能用，零安装零部署，交作业、演示、发给同学都方便；② 你以后自己改代码，原生 JS 比框架好下手——框架要先学它的规矩，原生 JS 改哪是哪；③ 需求很轻（4 个页面、3 次 AI 调用、本地存数据），上框架是杀鸡用牛刀。

### 2. 架构（模块划分＋数据流转）

```
┌─────────────────────────────────────────────┐
│  UI 层：4 个 Tab ＋ 全局设置                  │
│  Tab1 画像录入 / Tab2 分层洞察 / Tab3 话术生成 │
│  / Tab4 触达记录 / 设置（Key 自填、示例客户）  │
└──────────────┬──────────────────────────────┘
               │ 用户点"生成"
               ▼
┌─────────────────────────────────────────────┐
│  AI 调用模块：fetch 直调 AI Hub Mix           │
│  https://aihubmix.com/v1（OpenAI 兼容接口）   │
└──────────────┬──────────────────────────────┘
               │ 返回文本
               ▼
┌─────────────────────────────────────────────┐
│  工具模块：风险词标红 / 一键复制 / JSON 解析   │
└──────────────┬──────────────────────────────┘
               │ 人工确认后
               ▼
┌─────────────────────────────────────────────┐
│  数据模块：localStorage（浏览器本地小仓库）    │
│  存画像卡、话术、触达记录                     │
└─────────────────────────────────────────────┘
```

数据流转一句话：用户在页面上操作 → 需要 AI 干活时，页面直接给 AI Hub Mix 打电话 → AI 回话 → 页面展示 → 人工确认 → 存进浏览器本地。

### 3. 数据结构（localStorage 草图）

localStorage 是浏览器自带的小仓库，按"键值对"存文本。设计 4 把钥匙：

```js
// 钥匙1：画像卡 sp_profiles
[{ id, 称呼,
   基本信息: {年龄, 性别, 职业},
   行为特征: ["买过热玛吉", "客单价3万档", "二次到店意向高"],
   在意什么: "怕疼，做决定慢，需要安全感",
   上次聊到哪: "上次咨询过热玛吉但嫌贵",
   客户阶段: "活跃", 更新时间 }]

// 钥匙2：话术 sp_scripts
[{ id, 客户id, 表达对象: "亲切版",
   三版: [{版本: "正式版", 文本, 风险词: []}, ...],
   选中版本, 生成时间 }]

// 钥匙3：触达记录 sp_logs
[{ id, 客户id, 话术id, 渠道: "微信", 客户反应: "已回复", 发送时间 }]

// 钥匙4：设置 sp_settings
{ apiKey: "用户自填", 模型: "deepseek-chat", 分层阈值: {沉睡: 30, 流失: 90} }
```

### 4. 技术/工具

- 浏览器原生 `fetch` 发请求、`localStorage` 存数据、`Clipboard API` 做复制——全是浏览器自带的，不用装任何库。
- AI 能力：AI Hub Mix 的 OpenAI 兼容接口，你已经有 Key，沿用呆呆 Chat 的模式。

### 5. 优缺点和取舍

优点：零成本、零部署、双击即用；改代码快；Key 由使用者自填，不经过任何服务器，不存在"你的 Key 被别人拿到"的问题。

缺点（取舍）：① 数据只存在本机浏览器，换电脑/清缓存就没了——demo 阶段可接受；② Key 以明文存在本机——因为是使用者自己的 Key 自己填，可接受；③ 没有多用户、没有账号体系——demo 不需要。

### 6. 大白话

这个方案就是"**一个记事本加三通电话**"。记事本（localStorage）记下客户画像、话术和触达记录；需要 AI 干活时，打三通电话（3 个 AI 调用点）问 AI Hub Mix；电话费（API Key）各付各的，你填你的，我填我的，互不干扰。摆地摊：一个人、一张桌子、一本账，今天就开张。

## 方案 B：前后端分离（主选，demo 用）

### 1. 技术选型说明

- 前端：单文件 HTML（同方案 A 的页面，后面改成调自家后端）。
- 后端：Python Flask（轻，够用；以后量大了可换 FastAPI）。
- 数据库：SQLite（单文件数据库，零运维，2 核 4G 跑得轻松）。
- AI：千问百炼 OpenAI 兼容模式（`https://dashscope.aliyuncs.com/compatible-mode/v1`），model 用 `qwen-plus`，Key 存在后端环境变量 `BAILIAN_API_KEY`，前端碰不到。
- 为什么选 B：chen 有 2 核 4G 服务器且是运维出身，部署运维成本低；Key 藏后端更干净；前后端一次部署到位，Flask 同时把前端单文件托管了（访问一个地址就行）。

### 2. 架构（模块划分＋数据流转）

```
浏览器（页面） → Flask 后端 API → 千问百炼（OpenAI 兼容接口）
                        ↓
                   SQLite（单文件库）
```

数据流转：页面不再直调 AI，而是调自家后端 `/api/*`；后端拿着环境变量里的 Key 去调千问百炼，把结果存进 SQLite 再返回给页面。Key 藏在后端，前端碰不到。Flask 同时托管前端单文件，部署时只跑一个进程，访问一个地址就行。

### 3. 表结构草图

```sql
users      (id, 手机号, 密码哈希, 创建时间)          -- 账号体系
profiles   (id, user_id, 称呼, 基本信息JSON, 行为特征JSON,
            在意什么, 上次聊到哪, 客户阶段, 更新时间)
scripts    (id, profile_id, 表达对象, 三版JSON, 选中版本, 生成时间)
touch_logs (id, profile_id, script_id, 渠道, 客户反应, 发送时间)
```

### 4. 技术/工具

Flask/FastAPI ＋ SQLite；部署要一台云服务器（2核4G 起步）＋ 域名（https 回调用）。

### 5. 优缺点和取舍

优点：多端同步（手机电脑都能看）、多用户、Key 藏后端不暴露、可做定时任务（如每天自动提醒沉睡客户）。

缺点：要买服务器、要运维、要备案域名、有持续成本；开发慢（前后端联调）；demo 阶段全是多余的。

### 6. 大白话

方案 A 是摆地摊，方案 B 是**租店面开小卖部**：要装修（搭服务器）、要交租（云服务器按月付费）、要请人看店（运维）。好处是能接待很多客人（多用户）、账本不怕丢（数据库）、保险柜在里屋（Key 藏后端）。但你现在只是想验证"这个小吃好不好卖"，没必要先租店面。

## 选型结论

- **demo 用方案 B**（2026-10-11 chen 定稿）：Flask 后端（托管前端单文件＋API）＋ SQLite ＋ 千问百炼，部署在 chen 的 2 核 4G 服务器上。部署方式：Muse 生成部署提示词，chen 交给 AI 执行部署。
- 方案 A 保留为备选（零部署、改得快，万一服务器来不及可用 A 顶上交作业）。
- 面试话术：后端方案首先是成本决策——chen 有服务器且是运维出身，方案 B 的边际成本几乎为零，所以 demo 直接上 B；Key 藏后端也是 B 的附带好处。

## 你以后自己改代码，最容易踩的坑（方案 B 版）

1. **AI 返回的 JSON 可能"穿衣服"**：千问也经常把 JSON 包在 ```json 代码块里，后端必须先剥掉 markdown 包裹再 `json.loads`，否则 500。这是最常见的崩溃点。
2. **Key 放环境变量，别写进代码**：`BAILIAN_API_KEY` 从环境变量读，`.env` 文件不进 git、不发给别人。百炼的 Key 去百炼控制台自己申请，我不经手。
3. **百炼接口的 base_url 别拼错**：OpenAI 兼容模式是 `https://dashscope.aliyuncs.com/compatible-mode/v1`，注意是 `compatible-mode`，不是原生 dashscope 地址；model 用 `qwen-plus`。
4. **SQLite 并发写会锁库**：demo 单人用没问题；以后多人同时写，SQLite 会报 `database is locked`，那时再换 PostgreSQL。
5. **30 天/90 天阈值在后端配置**：PRD 说了 demo 暂不可配，想调改后端 `sp_settings` 默认值或 `config.py`。
6. **风险词表在后端**：要加词改后端的 `riskWords` 列表；只标红不拦截是 PRD 定的业务规则，不是 bug。
7. **部署后第一件事**：`curl /api/health` 通不通；再打开页面走一遍"录入→分层→话术→登记"闭环。
